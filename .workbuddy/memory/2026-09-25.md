# 2026-09-25

## 排查 00_sync-cherry-knowledge-directories.bat 退出码 1

**现象**：批处理每次运行都 `[batch-exit-code] 1`，但日志文件里完全没有批处理自身的输出。

**根因链（已验证）**：
1. `scripts/run-logged-batch.ps1` 用 `Start-Transcript` 记录，但 Transcript 抓不到批处理（原生进程）的 stdout —— 所以日志永远是空的，看不到任何报错。
2. 真正失败点是脚本 Step 2/3：`cherry-knowledge.ts sync-directories --refresh-existing --mode incremental --wait`，退出码 1，因为 8 个目录的刷新 job `failed`。
3. 这 8 个目录（播客 KB b1b701f5：菠萝健康派/硅谷101/津津乐道/津津有味/跨国串门儿计划/乱翻书/八分半第二季/畅所育言）的聚合错误是 "One or more child items failed"；下钻到 `knowledge_item` 表，31 个 file 条目的真实错误是 **"Bad Request"**。
4. `job` 表给出完整错误：`{"code":"JOB_HANDLER_THREW","message":"Bad Request","retryable":true}`，job type = `knowledge.index-documents`。
5. "Bad Request" 是 Ollama 返回的 HTTP 400，实际 body：
   `do embedding request: Post http://127.0.0.1:<port>/v1/embeddings: wsarecv: An existing connection was forcibly closed by the remote host`
   → **嵌入用的 llama-server 子进程在请求中途被杀/重启**（已用 8 次连续调用 `/v1/embeddings` 复现：第 7 次 400）。
6. 触发原因：Ollama 因显存大（~29.8 GiB）默认按 `num_ctx=262144` 预分配，而 qwen3-embedding:8b 训练上下文只有 40960；日志里反复出现
   `requested context size too large for model num_ctx=262144 n_ctx_train=40960` 和
   `llama-server model predicted to exceed available memory, evicting`，runner 每隔几秒被驱逐重启。

**不是**以下原因：脚本依赖文件齐全、Z: 可达、API key 存在、API 预检通过、文件本身是干净 UTF-8、文件大小也不是阈值（失败 20KB~172KB，成功的最大 560KB）。

## 已做的修改
- `scripts/run-logged-batch.ps1`：把批处理 stdout/stderr 通过管道接回 PowerShell 再 `Write-Host`，这样 Transcript 能记录全部输出；设 `CHERRY_KB_NO_PAUSE=1` 跳过 `pause`；UTF-8 编码。
  - 坑：`2>&1` + `$ErrorActionPreference='Stop'` 会把 tsx 写在 stderr 的进度行变成 ErrorRecord 并终止脚本，已在调用处临时改为 `Continue`。
- `00_sync-cherry-knowledge-directories.bat`：`if not exist "%PODCAST_SOURCE%\"` → `"%PODCAST_SOURCE%\."`（引号内尾反斜杠的 cmd 老坑）；`:finish` 前 `if defined CHERRY_KB_NO_PAUSE goto :done` 跳过 pause。

## 后续深挖：修正上面的第 6 点（num_ctx 不是根因）

用 `scripts/Modelfile.qwen3-embedding-8k` 建了 `qwen3-embedding-8k`（`FROM qwen3-embedding:8b` + `PARAMETER num_ctx 8192`），KV cache 从 ~5.7GB 降到 1152 MiB（`n_ctx_slot=8192` 已确认生效）。但**并发测试照样 400**，因此推翻了 num_ctx 假设。

**真正的根因（已用受控实验确认）**：并发。

- Cherry Studio 索引侧：`indexDocumentsJobHandler.ts` 里 `defaultConcurrency: 5`，`EMBEDDING_PROGRESS_BATCH_SIZE = 10`，AI SDK `embedMany` 默认无限并发 → 峰值约 **50 个并发 embedding 请求**。
- Ollama 侧：llama-server 以 `-np 1`（单 slot）启动。
- 实测（模型常驻 keep_alive=-1、无其他客户端干扰、串行打同一模型）：
  - 串行 30 次 → 3~5 次 400（约 85% 成功率）
  - 并发 8 → 大量 400 且请求挂起 120~180s
  - 并发 16 → 失败率约 50%
- 400 的 body 始终是 `do embedding request: ... wsarecv: An existing connection was forcibly closed by the remote host`，且每次 400 都紧跟着一次 `llama-server started`（runner 重启）。今天累计 644 个 400、1410 次 runner 重启。

**排除项**：显存充裕（32GB 卡只用了 15GB）；不是 CUDA 问题（建了 `num_gpu 0` 的 CPU 版模型，并发失败率一样）；不是模型文件所在盘的问题（I: 是本地固定磁盘）；不是输入内容问题（干净 UTF-8 固定文本也随机失败）。

**没能生效的尝试**：
- `OLLAMA_NUM_PARALLEL=4/8`：用户级 + 进程级都设过，重启 Ollama 两次，启动参数**始终还是 `-np 1`**，Ollama 0.34.1 忽略该变量。
- `LLAMA_ARG_FIT=off`：无改善。
- 独立起 `lib\ollama\llama-server.exe -np 8`：进程立刻退出，没起来。

**结论**：这是 Ollama 0.34.1 新 llama-server 引擎的稳定性问题，只能从「降低并发」或「换掉 Ollama」两侧解决。Cherry Studio 侧 `defaultConcurrency: 5` 是**硬编码**（`JobManager.ts` 读 `handler.defaultConcurrency ?? 1`，无配置项可覆盖），要改必须改源码 + 重建。

## 最终选择：降低 Cherry Studio 侧的索引并发

Ollama 侧改动已全部回滚（用户级 `OLLAMA_NUM_PARALLEL` / `OLLAMA_KEEP_ALIVE` 已删除；过程中为测试创建的 CPU 版模型 `qwen3-embedding-8k-cpu` 及其 Modelfile 已删除）。`qwen3-embedding-8k` 模型和 `scripts/Modelfile.qwen3-embedding-8k` 保留。

改了 `src/main/features/knowledge/tasks/indexDocumentsJobHandler.ts` 两处（唯一直接调 embedding 的 job handler，其余 handler 不调）：
- `EMBEDDING_PROGRESS_BATCH_SIZE` 10 → 1（每批只嵌一个 chunk）
- `defaultConcurrency` 5 → 1（队列串行）

目标是让 embedding 请求真正串行化，匹配 Ollama 的单 slot，绕过 0.34.1 的 llama-server 崩溃 bug。

## 构建环境备忘（本机容易踩的坑）

- **pnpm 不在 PATH**：没有全局安装，要用 `corepack pnpm`。递归调用 `pnpm run xxx` 会失败，需要先 `corepack enable` 生成 shim（已生成到 managed node 目录 `C:\Users\alexy\.workbuddy\binaries\node\versions\22.22.2-3\`）。
- **Node 版本**：项目要求 `>=24.11.1 <24.16.0`。Nodist 只有 20.10.0，可用的是 `C:\Program Files\nodejs\node.exe`（v24.18.0，超上限但只报 WARN 不影响构建）。跑构建时 PATH 前置这两个目录即可。

- 构建耗时约 45 秒（typecheck 三个工程 node/web/ai-core 全过）。
